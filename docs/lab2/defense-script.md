## Скриншоты 14–21. Разбор кода

### Модели (`internal/app/ds/`)

**`communal_resource.go`** — главная сущность. Показать структуру:

```go
type CommunalResource struct {
    ID uint `gorm:"primaryKey"`

    Name            string  `gorm:"type:varchar(100);not null"`
    Description     string  `gorm:"type:varchar(500)"`
    Status          string  `gorm:"type:varchar(15);not null;default:draft"`
    ImageURL        string  `gorm:"type:varchar(255)"`
    VideoURL        string  `gorm:"type:varchar(255)"`
    TariffRate      float64 `gorm:"type:numeric(10,2)"`
    ConsumptionNorm float64 `gorm:"type:numeric(10,3)"` // поле по теме
    MeasurementUnit string  `gorm:"type:varchar(20)"`

    CreatedAt   time.Time  `gorm:"not null"`
    PublishedAt *time.Time // nullable — заполняется только при публикации

    CreatorID uint `gorm:"not null"`
    Creator   User `gorm:"foreignKey:CreatorID"`
}
```

**Что сказать:** «Теги `gorm:"..."` — это описание колонки прямо в
Go-структуре: тип, длина, `not null`, значение по умолчанию. GORM
использует их и для генерации SQL при миграции, и для валидации при
записи. `PublishedAt` — указатель на время, а не просто время: это даёт
настоящий `NULL` в БД для ещё не опубликованных услуг, а не нулевую
дату».

**`user.go`** и **`like.go`** — показать коротко, обратить внимание на
`uniqueIndex:idx_user_resource` в `Like` — «Этот тег создаёт составной
уникальный индекс на паре полей — один пользователь не может лайкнуть
одну услугу дважды, ограничение задано на уровне БД, а не в коде
приложения».

### Репозиторий (`internal/app/repository/communal_resource.go`) — 5 методов через ORM + 1 сырой SQL

**1. `GetCommunalResources` (список, ORM)**
```go
query := r.db.Where("status = ?", ds.StatusPublished).Order("id")
if maxTariffRate != nil {
    query = query.Where("tariff_rate <= ?", *maxTariffRate)
}
var resources []ds.CommunalResource
query.Find(&resources)
```
«Фильтрация полностью на стороне БД: если фильтр по тарифу задан,
добавляется ещё одно условие `WHERE`, и в приложение приходит уже готовый
отфильтрованный список».

**2. `GetCommunalResourceFeedItem` (лента, ORM)**
```go
case next:
    r.db.Where("status = ? AND id > ?", ds.StatusPublished, id).
        Order("id").First(&resource)
    // если после последней — начинаем сначала
```
«Здесь важный момент: метод всегда возвращает из БД ровно одну строку —
никакого перебора списка в коде. Переход "следующая после X" делается
условием `id > X` с сортировкой и `LIMIT 1` (это и есть `First`). Если
такой строки нет — значит, дошли до конца списка, и отдельным запросом
берём самую первую услугу, то есть зацикливаемся».

**3. `GetCommunalResourceDraft` (получение черновика, ORM)**
```go
r.db.Where("status = ? AND creator_id = ?", ds.StatusDraft, creatorID).First(&draft)
```
«Ищем черновик конкретного создателя. Если его нет — это не ошибка
уровня приложения, а нормальная ситуация: тогда `/add` покажет форму
создания, а не публикации».

**4. `CreateCommunalResourceDraft` (POST /add, ORM)**
```go
draft := ds.CommunalResource{Name: name, Status: ds.StatusDraft, CreatorID: creatorID, CreatedAt: time.Now()}
r.db.Create(&draft)
```
«Простой `INSERT` через ORM — создаём черновик с одним заполненным полем,
остальные получают значения по умолчанию из тегов структуры».

**5. `PublishCommunalResource` (POST /publish, ORM)**
```go
r.db.Model(&ds.CommunalResource{}).
    Where("id = ? AND status = ?", id, ds.StatusDraft).
    Updates(map[string]any{ ... "status": ds.StatusPublished, "published_at": now })
```
«Один `UPDATE` через ORM, который одновременно заполняет описание, оба
поля по теме, единицу измерения и меняет статус. Условие `AND status =
draft` в `WHERE` — защита от повторной публикации уже опубликованной
услуги».

**6. `DeleteCommunalResource` (POST /delete-resource, СЫРОЙ SQL, без ORM)**
```go
r.db.Exec("UPDATE communal_resources SET status = ? WHERE id = ?", ds.StatusDeleted, id)
```
«А это единственный метод, где я сознательно не использую построитель
запросов GORM, а пишу SQL-строку напрямую через `Exec` — это и есть
требование методички "удаление через SQL UPDATE, без ORM"».

**Что сказать в целом про архитектуру:** «Структура — chistая
архитектура в три слоя: `ds` (модели/структуры данных, ничего не знают
про HTTP или БД), `repository` (только здесь есть обращения к GORM и
SQL), `handler` (разбирает HTTP-запрос, вызывает репозиторий, формирует
ответ). Слои не смешиваются — handler никогда не пишет SQL напрямую,
repository никогда не знает про `gin.Context`».

## Контрольные вопросы — краткие ответы

**Виды БД.** Реляционные (PostgreSQL, MySQL) — данные в таблицах со
связями по ключам, строгая схема. Документные (MongoDB) — JSON-подобные
документы без жёсткой схемы. Ключ-значение (Redis) — быстрый доступ по
ключу. Графовые (Neo4j) — узлы и связи, для сложных взаимосвязей. В
проекте — PostgreSQL, потому что данные хорошо ложатся на таблицы со
связями (услуги — пользователи — лайки).

**SQL-запросы.** Группы: DDL (`CREATE`, `ALTER` — структура), DML
(`SELECT`, `INSERT`, `UPDATE`, `DELETE` — данные), DCL (`GRANT`,
`REVOKE` — права). В проекте DML используется и через ORM (`Find`,
`Create`, `Updates`), и напрямую (`Exec` для удаления).

**Курсоры.** Механизм построчного обхода результата запроса на стороне
БД, без загрузки всего набора в память сразу — полезно для больших
выборок. В методичке лабораторной 2 этим словом называют вообще прямое
выполнение SQL в обход ORM (`db.Raw(...).Row()` / `db.Exec(...)`).

**ORM.** Object-Relational Mapping — связывает строки таблиц с объектами
языка программирования. Преимущества: меньше ручного SQL, защита от SQL-
инъекций через параметризацию, переносимость между СУБД. Недостатки:
не всегда оптимальный SQL «из коробки», сложные запросы иногда проще и
быстрее написать руками (поэтому удаление в проекте — сырой SQL).

**Модель и миграция.** Модель — Go-структура с тегами `gorm`, описывающая
таблицу. Миграция — процесс приведения схемы БД в соответствие с
моделями; в проекте это `cmd/migrate/main.go`, вызывающий
`db.AutoMigrate(&ds.User{}, &ds.CommunalResource{}, &ds.Like{})`.

**Чистая архитектура.** Разделение на независимые слои с однонаправленной
зависимостью: `handler` зависит от `repository`, `repository` зависит от
`ds`, но не наоборот. Позволяет менять один слой (например, СУБД или
веб-фреймворк), не трогая остальные.

# Полный разбор кода лабораторной работы 2

Ниже — весь код, добавленный/изменённый во второй лабораторной, в порядке
«от запуска до ответа», с объяснением каждого файла. Если читать сверху
вниз — ровно так, как физически выполняется программа при старте и при
одном HTTP-запросе.

## Структура каталогов

```
cmd/
  utility-bills/main.go   точка входа приложения (веб-сервер)
  migrate/main.go         отдельная утилита миграций БД
internal/
  app/
    config/config.go      чтение config.toml
    dsn/dsn.go             сборка строки подключения к Postgres
    ds/                    модели (структуры данных = таблицы БД)
    repository/            доступ к БД (GORM + сырой SQL)
    handler/               HTTP-обработчики (Gin)
  pkg/app.go               сборка приложения и запуск сервера
config/config.toml        параметры хоста/порта
```

Главный принцип чистой архитектуры здесь: **зависимости идут только
внутрь**. `handler` знает про `repository`, `repository` знает про `ds`,
но `ds` не знает вообще ни про что — это просто описание данных.
`main.go` — единственное место, которое видит все слои сразу и склеивает
их вместе.

## 1. Запуск: `cmd/utility-bills/main.go`

```go
func main() {
    router := gin.Default()                       // HTTP-роутер Gin

    conf, err := config.NewConfig()                // читает config/config.toml
    repo, err := repository.New(dsn.FromEnv())     // подключается к Postgres
    h := handler.NewHandler(repo)                  // обработчики + репозиторий

    application := pkg.NewApp(conf, router, h)
    application.RunApp()                           // регистрирует маршруты и слушает порт
}
```

Что происходит по шагам:
1. Создаётся пустой роутер Gin.
2. Читается конфиг (хост/порт сервера) — `config.NewConfig()`.
3. Открывается подключение к базе — `repository.New(dsn.FromEnv())`.
   Если Postgres недоступен, приложение упадёт здесь же с понятной
   ошибкой (`logrus.Fatalf`), а не позже на первом запросе.
4. Создаётся `Handler`, в который «внедряется» уже готовый репозиторий —
   это называется **dependency injection**: хендлер не создаёт
   зависимость сам, а получает её снаружи, что упрощает тестирование и
   замену реализации.
5. `pkg.NewApp` склеивает конфиг + роутер + хендлер в одну структуру
   `Application`, `RunApp()` запускает сервер.

## 2. Конфигурация: `internal/app/config/config.go` и `config/config.toml`

`config.toml`:
```toml
ServiceHost = "0.0.0.0"
ServicePort = 8080
```

`config.go` читает этот файл через библиотеку **viper** и превращает его
в Go-структуру `Config{ServiceHost, ServicePort}`. Отдельно вызывается
`godotenv.Load()` — это подтягивает переменные из `.env` в окружение
процесса (`os.Getenv` дальше их увидит).

Зачем два разных механизма конфигурации (`.toml` — для сервера, `.env` —
для БД)? Так исторически показано в методичке: параметры самого сервиса
(на каком порту слушать) — в файле конфигурации; секреты и параметры
подключения к внешним системам (пароль от БД) — в переменных окружения,
чтобы их было легко подменить при разворачивании (и не закоммитить
случайно в git — `.env` в `.gitignore`).

## 3. Строка подключения к БД: `internal/app/dsn/dsn.go`

```go
func FromEnv() string {
    host := os.Getenv("DB_HOST")
    ...
    return fmt.Sprintf("host=%s port=%s user=%s password=%s dbname=%s sslmode=disable", ...)
}
```

Просто читает 5 переменных окружения (`DB_HOST`, `DB_PORT`, `DB_USER`,
`DB_PASS`, `DB_NAME`) и склеивает их в DSN-строку — формат, который
понимает драйвер PostgreSQL. Если `DB_HOST` пустой — значит, `.env` не
подключился, и функция возвращает пустую строку (это сразу даст понятную
ошибку подключения, а не странное поведение).

## 4. Модели (`internal/app/ds/`) — три файла, три таблицы

Пакет называется `ds` (data structures) по соглашению из методички курса.
Каждая структура через теги `gorm:"..."` одновременно:
- описывает Go-тип для работы в коде;
- описывает колонку БД для автоматической миграции (`AutoMigrate`);
- задаёт ограничения (`not null`, `unique`, значение по умолчанию).

**`communal_resource.go`** — уже разобран выше (скриншоты 14-21).
Дополнительно: метод `TableName()` переопределяет имя таблицы —
без него GORM сам бы вывел имя из названия структуры (`communal_resources`
он бы и так угадал по правилам плюрализации, но `Like`→`likes` и
`User`→`users` можно было бы перепутать с `like`/`user` в единственном
числе, поэтому имя таблицы у всех трёх моделей задано явно).

**`user.go`**:
```go
type User struct {
    ID          uint   `gorm:"primaryKey" json:"id"`
    Login       string `gorm:"type:varchar(50);unique;not null" json:"login"`
    Password    string `gorm:"type:varchar(100);not null" json:"-"`
    IsModerator bool   `gorm:"type:boolean;not null;default:false" json:"isModerator"`
}
```
`json:"-"` у пароля — если структуру когда-нибудь сериализовать в JSON
(например, для будущего REST API в лабораторной 3), пароль не попадёт в
ответ. `unique` на логине — на уровне БД гарантирует, что двух
одинаковых логинов быть не может, даже если в коде забыть проверку.

**`like.go`**:
```go
type Like struct {
    ID uint `gorm:"primaryKey"`
    UserID             uint `gorm:"not null;uniqueIndex:idx_user_resource"`
    CommunalResourceID uint `gorm:"not null;uniqueIndex:idx_user_resource"`
    User             User             `gorm:"foreignKey:UserID"`
    CommunalResource CommunalResource `gorm:"foreignKey:CommunalResourceID"`
}
```
Связующая таблица классического отношения «многие ко многим»: у одной
услуги может быть много лайков, у одного пользователя — много лайков на
разных услугах. Одинаковый `uniqueIndex:idx_user_resource` на двух полях
создаёт **составной** уникальный индекс на паре — это защита от дубля
лайка средствами БД, без единого `if` в коде приложения. Поля `User` и
`CommunalResource` — это не колонки, а связи для удобной загрузки
(GORM association), сама структура таблицы описывается только `UserID`
и `CommunalResourceID`.

## 5. Репозиторий (`internal/app/repository/`) — два файла

**`repository.go`** — просто конструктор:
```go
type Repository struct { db *gorm.DB }

func New(dsn string) (*Repository, error) {
    db, err := gorm.Open(postgres.Open(dsn), &gorm.Config{})
    return &Repository{db: db}, err
}
```
Открывает соединение с Postgres через драйвер `gorm.io/driver/postgres` и
прячет объект `*gorm.DB` внутри структуры `Repository` — весь остальной
код обращается к базе только через методы `Repository`, никогда не видя
`*gorm.DB` напрямую. Это и есть смысл слоя: если завтра поменяется СУБД
или ORM, поменяется только этот пакет, а `handler` не заметит разницы.

**`communal_resource.go`** — шесть методов, разобраны выше подробно
(раздел «Скриншоты 14-21»). Кратко ещё раз, что делает каждый:

| Метод | HTTP-метод/маршрут | Как | Что делает |
|---|---|---|---|
| `GetCommunalResources` | `GET /` | ORM | список опубликованных + фильтр по тарифу |
| `GetCommunalResourceFeedItem` | `GET /feed/:id` | ORM | одна услуга или «следующая», одним запросом |
| `GetCommunalResourceDraft` | `GET /add` | ORM | черновик текущего создателя (или nil) |
| `CreateCommunalResourceDraft` | `POST /add` | ORM | создаёт черновик по названию |
| `PublishCommunalResource` | `POST /publish` | ORM | заполняет поля, меняет статус на published |
| `DeleteCommunalResource` | `POST /delete-resource` | сырой SQL | логическое удаление (status → deleted) |

Плюс вспомогательный `GetLikesCount(resourceID)` — считает строки в
`likes` для конкретной услуги (`SELECT COUNT(*) ... WHERE
communal_resource_id = ?`), используется и на плитке, и в ленте.

## 6. Обработчики (`internal/app/handler/`) — два файла

**`handler.go`** — «рамка»: структура `Handler`, конструктор, регистрация
маршрутов, обработка ошибок.

```go
func (h *Handler) RegisterHandler(router *gin.Engine) {
    router.GET("/", h.Tile)
    router.GET("/feed", h.Feed)
    router.GET("/feed/:id", h.Feed)
    router.GET("/add", h.Add)
    router.POST("/add", h.CreateDraft)
    router.POST("/publish", h.Publish)
    router.POST("/delete-resource", h.Delete)
}
```
Здесь буквально видна вся карта маршрутов приложения — семь строк, семь
URL. Обратите внимание: `/feed` и `/feed/:id` — это **один и тот же**
метод-обработчик `h.Feed`, просто с параметром или без (id=0 внутри
хендлера означает «без параметра»).

`RegisterStatic` подключает html-шаблоны (`templates/*`) и статику
(картинки/CSS из `resources/`) — без этого вызова Gin не найдёт `.html`
файлы и не отдаст `/static/...`.

`errorHandler` — общая точка для ответа об ошибке: логирует в консоль
(`logrus.Error`) и отдаёт клиенту JSON с кодом ошибки. Используется во
всех обработчиках, чтобы не дублировать одинаковый код обработки ошибок.

**`communal_resource.go`** — сама логика страниц. Разберём по одному
обработчику:

### `resourceView` и `toView` — склейка данных для шаблонов
```go
type resourceView struct {
    ds.CommunalResource
    LikesCount      int64
    DisplayImageURL string
}
```
`ds.CommunalResource` встроена без имени поля (embedding) — это значит,
что все поля модели (`Name`, `TariffRate`, ...) доступны в шаблоне
напрямую через `.Name`, `.TariffRate`, как будто это поля самого
`resourceView`. К ним просто добавляются два вычисляемых поля: число
лайков и картинка с фолбэком на заглушку. `toView()` — единственное
место, где эта склейка происходит, поэтому и на плитке, и в ленте лайки
и заглушка считаются одинаково, без дублирования логики.

### `Tile` — GET /
1. Читает `?tariff=` из query-строки.
2. Если параметр есть и парсится как число — передаёт его в репозиторий
   как `maxTariffRate`, иначе оставляет `nil` (без фильтра).
3. Получает список из репозитория, оборачивает каждую запись в
   `resourceView` через `toView`.
4. Рендерит `tile.html`, передавая список карточек и исходное значение
   фильтра (`Tariff`) — чтобы поле ввода не очищалось после поиска.

### `Feed` — GET /feed и /feed/:id
1. Достаёт `id` из URL (`ctx.Param("id")`) — если параметра нет
   (маршрут `/feed`), `id` остаётся нулём.
2. Читает `?next=true` из query-строки.
3. Вызывает `GetCommunalResourceFeedItem(id, next)` — вся логика «какую
   именно услугу показать» живёт в репозитории, хендлер просто
   передаёт параметры дальше.
4. Если услуга не найдена (удалена или несуществующий id) — отдаёт 404
   с текстом «услуга не найдена», без падения приложения.

### `Add` — GET /add
Просто спрашивает у репозитория черновик текущего пользователя и отдаёт
его в шаблон. Вся развилка «форма создания или форма публикации» решается
**в самом шаблоне** (`{{ if .Draft }}`) — хендлер знает только «черновик
есть» или «черновика нет (nil)».

### `CreateDraft` — POST /add
Читает одно поле формы (`name`) через `ctx.PostForm`, создаёт черновик,
редиректит обратно на `/add` — GET-запрос после редиректа уже увидит
только что созданный черновик и покажет форму публикации. Это стандартный
веб-паттерн **Post/Redirect/Get**: он не даёт браузеру повторно отправить
ту же форму при обновлении страницы (F5).

### `Publish` — POST /publish
Читает пять полей формы, при этом числовые (`tariffRate`,
`consumptionNorm`) явно парсятся через `strconv.ParseFloat` — если
пользователь введёт не число, вернётся понятная ошибка 400, а не падение
в SQL. Дальше — один вызов репозитория и редирект на плитку.

### `Delete` — POST /delete-resource
Симметрично `Publish`, но проще: только `id`, вызов
`DeleteCommunalResource`, редирект на `/`.

## 7. Миграции: `cmd/migrate/main.go`

Отдельная маленькая программа, никак не связанная с веб-сервером:
```go
db, _ := gorm.Open(postgres.Open(dsn.FromEnv()), &gorm.Config{})
db.AutoMigrate(&ds.User{}, &ds.CommunalResource{}, &ds.Like{})
```
Подключается к той же базе и просит GORM свериться: для каждой
структуры — существует ли таблица, все ли колонки на месте, совпадают ли
типы. Если чего-то не хватает — `AutoMigrate` выполнит нужные `CREATE
TABLE`/`ALTER TABLE` сам. Запускается вручную командой `go run
./cmd/migrate`, отдельно от `go run ./cmd/utility-bills` — веб-сервер
миграции не запускает сам, это осознанное разделение: на проде
миграции обычно накатывают отдельным контролируемым шагом, а не при
каждом старте приложения.

Порядок в списке `AutoMigrate` не случаен: `User` идёт первым, потому
что на него ссылаются внешние ключи из `CommunalResource` и `Like` —
таблица, на которую ссылаются, должна существовать раньше таблицы со
ссылкой.

## 8. Инфраструктура: `docker-compose.yml`

Секция, добавленная в лабораторной 2 (рядом с уже существовавшим MinIO
из лабы 1):
```yaml
postgres:
  image: postgres:16
  ports:
    - "5433:5432"      # порт сдвинут, на машине уже был нативный Postgres
  environment:
    POSTGRES_USER: ${DB_USER}
    POSTGRES_PASSWORD: ${DB_PASS}
    POSTGRES_DB: ${DB_NAME}
  volumes:
    - postgres-data:/var/lib/postgresql/data   # данные переживают перезапуск контейнера

adminer:
  image: adminer:latest
  ports:
    - "8081:8080"
  depends_on:
    - postgres
```
`depends_on` гарантирует, что Docker поднимет `postgres` раньше, чем
`adminer` (хотя и не ждёт полной готовности БД — только запуска
контейнера). Переменные `${DB_USER}` и т.д. подставляются из `.env` —
тот же файл, который читает Go-приложение через `dsn.FromEnv()`, так что
имя пользователя и пароль в контейнере и в приложении всегда совпадают.

## Как это всё работает вместе — путь одного запроса

На примере открытия плитки в браузере (`GET /`):

1. Браузер → Gin router → находит обработчик `h.Tile` (зарегистрирован в
   `handler.go`).
2. `h.Tile` разбирает query-параметр `tariff`, зовёт
   `h.Repository.GetCommunalResources(maxTariffRate)`.
3. `Repository` строит запрос через GORM (`Where(...).Order(...).Find(...)`)
   — GORM превращает это в SQL и отправляет в Postgres через драйвер
   `pgx`.
4. Postgres возвращает строки → GORM превращает их обратно в срез
   `[]ds.CommunalResource`.
5. `h.Tile` оборачивает каждую запись в `resourceView` (добавляя лайки
   и картинку-заглушку при необходимости) — здесь снова происходит
   отдельный запрос к БД на каждую карточку (`GetLikesCount`).
6. Gin рендерит `templates/tile.html`, подставляя `Resources` и `Tariff`
   в `html/template`, отдаёт готовый HTML браузеру.

Ни на одном из этих шагов нет ни одного места, где данные фильтруются
или пересчитываются в Go-массивах вручную — вся логика выборки лежит в
SQL-запросах, а Go-код только дирижирует вызовами и раскладывает
результат по шаблону.
