## Скриншоты 1–2. Adminer — логическое удаление и select

**Что показывать:** открыть `localhost:8081`, зайти в базу
`utility_bills`, открыть таблицу `communal_resources`.

**Что сказать:** «Показываю панель администрирования Adminer. Выполняю
SQL-запрос, который меняет статус услуги на "удалён" — это логическое
удаление, запись остаётся в базе, просто перестаёт быть видна
пользователям».

```sql
UPDATE communal_resources SET status = 'deleted' WHERE id = <любой опубликованный>;
SELECT id, name, status FROM communal_resources ORDER BY id;
```

Показать `select` — видно новый статус `deleted`.

## Скриншоты 3–10. Три страницы приложения

Открыть `localhost:8080` в браузере (в режиме инкогнито или с отключённым
кешем в DevTools — Network → Disable cache, чтобы не ловить старые версии
страниц).

1. **Поиск/фильтр.** `/?tariff=10` — «Фильтр работает на бэкенде, одним
   SQL-запросом с условием `tariff_rate <= ?`, а не перебором массива на
   клиенте».
2. **Удалить услугу.** Нажать крестик на карточке плитки — «Кнопка
   вызывает `POST /delete-resource`, который выполняет прямой SQL
   `UPDATE`, без ORM — это отдельное требование методички именно для
   этого метода».
3. **Перейти по url удалённой услуги.** Открыть `/feed/<id>` только что
   удалённой — «Услуга в статусе deleted не отдаётся: метод ленты
   фильтрует по `status = 'published'`, поэтому получаем "услуга не
   найдена"».
4. **Добавить услугу.** `/add` без черновика → ввести название → «Далее»
   — «Форма создания принимает только название: фото и видео в этой
   лабораторной по методичке не сохраняются, только текстовое поле».
5. **Select в БД после создания.** В Adminer — `SELECT * FROM
   communal_resources WHERE id = <новый>;` — «Статус черновика — draft,
   создатель проставлен константой, пока нет авторизации».
6. **Опубликовать карточку.** Вернуться на `/add` — там уже форма
   публикации с заполненным именем — заполнить описание, тариф, норматив,
   единицу измерения → «Опубликовать» — «Метод меняет статус на published
   и одним UPDATE заполняет остальные поля через ORM».
7. **Снова select в БД.** Тот же id — статус теперь `published`, поля
   заполнены.

## Скриншоты 14–21. Разбор кода

### Модели (`internal/app/ds/`)

**`communal_resource.go`** — главная сущность. Показать структуру:

```go
type CommunalResource struct {
    ID uint `gorm:"primaryKey"`

    Name            string  `gorm:"type:varchar(100);not null"`
    Description     string  `gorm:"type:varchar(500)"`
    Status          string  `gorm:"type:varchar(15);not null;default:draft"`
    ImageURL        string  `gorm:"type:varchar(255)"`
    VideoURL        string  `gorm:"type:varchar(255)"`
    TariffRate      float64 `gorm:"type:numeric(10,2)"`
    ConsumptionNorm float64 `gorm:"type:numeric(10,3)"` // поле по теме
    MeasurementUnit string  `gorm:"type:varchar(20)"`

    CreatedAt   time.Time  `gorm:"not null"`
    PublishedAt *time.Time // nullable — заполняется только при публикации

    CreatorID uint `gorm:"not null"`
    Creator   User `gorm:"foreignKey:CreatorID"`
}
```

**Что сказать:** «Теги `gorm:"..."` — это описание колонки прямо в
Go-структуре: тип, длина, `not null`, значение по умолчанию. GORM
использует их и для генерации SQL при миграции, и для валидации при
записи. `PublishedAt` — указатель на время, а не просто время: это даёт
настоящий `NULL` в БД для ещё не опубликованных услуг, а не нулевую
дату».

**`user.go`** и **`like.go`** — показать коротко, обратить внимание на
`uniqueIndex:idx_user_resource` в `Like` — «Этот тег создаёт составной
уникальный индекс на паре полей — один пользователь не может лайкнуть
одну услугу дважды, ограничение задано на уровне БД, а не в коде
приложения».

### Репозиторий (`internal/app/repository/communal_resource.go`) — 5 методов через ORM + 1 сырой SQL

**1. `GetCommunalResources` (список, ORM)**
```go
query := r.db.Where("status = ?", ds.StatusPublished).Order("id")
if maxTariffRate != nil {
    query = query.Where("tariff_rate <= ?", *maxTariffRate)
}
var resources []ds.CommunalResource
query.Find(&resources)
```
«Фильтрация полностью на стороне БД: если фильтр по тарифу задан,
добавляется ещё одно условие `WHERE`, и в приложение приходит уже готовый
отфильтрованный список».

**2. `GetCommunalResourceFeedItem` (лента, ORM)**
```go
case next:
    r.db.Where("status = ? AND id > ?", ds.StatusPublished, id).
        Order("id").First(&resource)
    // если после последней — начинаем сначала
```
«Здесь важный момент: метод всегда возвращает из БД ровно одну строку —
никакого перебора списка в коде. Переход "следующая после X" делается
условием `id > X` с сортировкой и `LIMIT 1` (это и есть `First`). Если
такой строки нет — значит, дошли до конца списка, и отдельным запросом
берём самую первую услугу, то есть зацикливаемся».

**3. `GetCommunalResourceDraft` (получение черновика, ORM)**
```go
r.db.Where("status = ? AND creator_id = ?", ds.StatusDraft, creatorID).First(&draft)
```
«Ищем черновик конкретного создателя. Если его нет — это не ошибка
уровня приложения, а нормальная ситуация: тогда `/add` покажет форму
создания, а не публикации».

**4. `CreateCommunalResourceDraft` (POST /add, ORM)**
```go
draft := ds.CommunalResource{Name: name, Status: ds.StatusDraft, CreatorID: creatorID, CreatedAt: time.Now()}
r.db.Create(&draft)
```
«Простой `INSERT` через ORM — создаём черновик с одним заполненным полем,
остальные получают значения по умолчанию из тегов структуры».

**5. `PublishCommunalResource` (POST /publish, ORM)**
```go
r.db.Model(&ds.CommunalResource{}).
    Where("id = ? AND status = ?", id, ds.StatusDraft).
    Updates(map[string]any{ ... "status": ds.StatusPublished, "published_at": now })
```
«Один `UPDATE` через ORM, который одновременно заполняет описание, оба
поля по теме, единицу измерения и меняет статус. Условие `AND status =
draft` в `WHERE` — защита от повторной публикации уже опубликованной
услуги».

**6. `DeleteCommunalResource` (POST /delete-resource, СЫРОЙ SQL, без ORM)**
```go
r.db.Exec("UPDATE communal_resources SET status = ? WHERE id = ?", ds.StatusDeleted, id)
```
«А это единственный метод, где я сознательно не использую построитель
запросов GORM, а пишу SQL-строку напрямую через `Exec` — это и есть
требование методички "удаление через SQL UPDATE, без ORM"».

**Что сказать в целом про архитектуру:** «Структура — chistая
архитектура в три слоя: `ds` (модели/структуры данных, ничего не знают
про HTTP или БД), `repository` (только здесь есть обращения к GORM и
SQL), `handler` (разбирает HTTP-запрос, вызывает репозиторий, формирует
ответ). Слои не смешиваются — handler никогда не пишет SQL напрямую,
repository никогда не знает про `gin.Context`».

## ER-диаграмма (StarUML)

Три таблицы: `communal_resources`, `likes`, `users`. Связи 1—* от
`users` к `communal_resources` (создатель) и к `likes`, и от
`communal_resources` к `likes`. Каскадное удаление нигде не используется
— удаление только логическое, через поле `status`.

## Контрольные вопросы — краткие ответы

**Виды БД.** Реляционные (PostgreSQL, MySQL) — данные в таблицах со
связями по ключам, строгая схема. Документные (MongoDB) — JSON-подобные
документы без жёсткой схемы. Ключ-значение (Redis) — быстрый доступ по
ключу. Графовые (Neo4j) — узлы и связи, для сложных взаимосвязей. В
проекте — PostgreSQL, потому что данные хорошо ложатся на таблицы со
связями (услуги — пользователи — лайки).

**SQL-запросы.** Группы: DDL (`CREATE`, `ALTER` — структура), DML
(`SELECT`, `INSERT`, `UPDATE`, `DELETE` — данные), DCL (`GRANT`,
`REVOKE` — права). В проекте DML используется и через ORM (`Find`,
`Create`, `Updates`), и напрямую (`Exec` для удаления).

**Курсоры.** Механизм построчного обхода результата запроса на стороне
БД, без загрузки всего набора в память сразу — полезно для больших
выборок. В методичке лабораторной 2 этим словом называют вообще прямое
выполнение SQL в обход ORM (`db.Raw(...).Row()` / `db.Exec(...)`).

**ORM.** Object-Relational Mapping — связывает строки таблиц с объектами
языка программирования. Преимущества: меньше ручного SQL, защита от SQL-
инъекций через параметризацию, переносимость между СУБД. Недостатки:
не всегда оптимальный SQL «из коробки», сложные запросы иногда проще и
быстрее написать руками (поэтому удаление в проекте — сырой SQL).

**Модель и миграция.** Модель — Go-структура с тегами `gorm`, описывающая
таблицу. Миграция — процесс приведения схемы БД в соответствие с
моделями; в проекте это `cmd/migrate/main.go`, вызывающий
`db.AutoMigrate(&ds.User{}, &ds.CommunalResource{}, &ds.Like{})`.

**Чистая архитектура.** Разделение на независимые слои с однонаправленной
зависимостью: `handler` зависит от `repository`, `repository` зависит от
`ds`, но не наоборот. Позволяет менять один слой (например, СУБД или
веб-фреймворк), не трогая остальные.
